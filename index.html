02 / ENGINEERING CONTRIBUTIONS

Two backends. Two optimization strategies.

NPU / COMPILER & SCHEDULING

Keep the residual chain on chip.

Conv2 was inexpensive to compute but expensive to keep alive: the main path and Add23 needed different regions of a large feature tensor.

  1. 01

    Expose the available parallelism

    Use six physical compute tiles, then identify the remaining data-flow costs in the compiler plan.

  2. 02

    Repair shared views and halo coverage

    Union both consumers’ halo needs, preserve per-cluster offsets, and alias covered CMX subviews instead of materializing copies.

  3. 03

    Tune the complete residual group

    One Conv2 computation per block. Fifteen column groups and H6 scheduling avoid planned Conv2/Conv21 writeback and explicit spills.

Compiler approach ↗
GPU / LAYOUT & KERNEL FUSION

Preserve the fast convolution path.

The native GPU convolutions already fused ReLU and the residual Add. The adopted change targets avoidable work after Conv25.

  1. 01

    Read Conv25 in its native output layout

    Consume the BYXF FP16 tensor directly, eliminating the extra format-reorder and DepthToSpace intermediate tensors.

  2. 02

    Fuse the complete output transformation

    One OpenCL kernel performs PixelShuffle ×2, clamps to [0,1], and writes the complete FP32 output.

  3. 03

    Verify what the compiler actually emitted

    Inspect runtime graphs, exported binaries and machine instructions. Retain the native seven-convolution implementation.

03 / MEASURED RESULTS

Latency gains with the output held constant.

15 ms target

Full-output validation. Each adopted artifact passed all six frames before and after timing. The exported GPU artifact also passed fresh-process import verification.

Throughput is a separate result. Two queued NPU requests reached 14.92 / 14.88 ms per frame, with roughly 29.8 ms submission-to-completion latency. That is not 15 ms single-frame latency.

04 / A USEFUL FAILED EXPERIMENT

Shared memory was only the beginning.

Research path · not adopted

A cross-convolution SLM kernel kept features on chip but initially took 311 ms. Disassembly exposed scalar gathers, repeated address calculations and insufficient matrix reuse.

INITIAL EXPERIMENT

M8 × N16

Eight activation gathers and eight weight gathers around a main DPAS; coordinates recomputed inside the K loop.

→
REVISED DATA PATH

M32 × N32

Row blocks, subgroup block IO, GRF256, input preloading and residual block reads. Identical reference output bits.

14.8× faster within this experimental route. At 21.00 ms it still lost to the adopted 17.58 ms GPU path, so it did not replace that artifact.

What the timestamps establish — and what they do not

In the initial kernel, the two layer barriers represented 3.42–3.52% of sampled subgroup spans in the early group and 3.14–3.27% in the late group. Most sampled span remained inside convolution stages, including fetch, address calculation, computation and waiting.

These are subgroup timestamp shares, not fractions of single-frame wall time. No claim is made for a separately measured DMA, physical DDR, halo or instruction-stall breakdown.

Conv2 reconstruction preserved all six outputs but took 28.30 ms. Explicit device output binding introduced extra layout operations. Loop unrolling and same-weight instruction ordering gave no further measured gain.
